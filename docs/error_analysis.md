# 误判案例分析

> 在本数据集（20 条）上检测器达到 **Precision = Recall = F1 = 1.0**，无漏检无误报。  
> 本文档不记录"真正的误判"，而是分析**边界 case**（在规则化方法下"差一点就误判"或"分类归属容易摇摆"的样本），以及**规则变动时容易导致误判的点**。

---

## 一、容易误判的高危 case（按实际命中规则归类）

### 1.1 `h04` 发票政策 — "部分否定 + 部分肯定"型（差点漏检）

| 维度 | 内容 |
|---|---|
| KB | 发票政策：支持电子发票，下单后在订单详情页申请。**暂不支持纸质发票**。 |
| Reply | 可以的，支持电子发票**和纸质发票**。下单时在备注里写上发票抬头和税号就行。 |
| Ground Truth | 政策偏差 |
| 我的判定 | 事实编造（R_KB_DENY_REPLY_AFFIRM） |

**为什么容易漏检？**
- KB 既包含肯定（"支持电子发票"）又包含否定（"暂不支持纸质发票"），规则必须识别**否定对象**并对比 reply 中该对象的语境。
- 最初版本的 R_NEG_AFFIRM 太宽泛，导致这种"混合"型 case 漏检。
- 一旦把 R_NEG_AFFIRM 收窄到"KB 含强否定 + reply 含肯定"，又会带来 h12 类误报。

**修复方案**：独立的 R_KB_DENY_REPLY_AFFIRM 规则：
1. 从 KB 中提取被否定的对象 X（"暂不支持 X" / "不支持 X"）
2. 检查 reply 中 X 出现的位置，前后 30 字符内是否有"不支持 / 暂不支持"等否定词
3. 若 X 出现但附近没有否定 → 编造

**仍可能误判的情形**：KB 中"不支持 X"中的 X 与 reply 中出现的 X 字面相同但语义不同（如 KB "不支持 32 位系统" 与 reply "不支持 X，但 64 位系统可以"）。

### 1.2 `h12` 货到付款 — "否定同一对象 + 肯定其他对象"型（差点误报）

| 维度 | 内容 |
|---|---|
| KB | 支付方式：微信支付、支付宝、银行卡、花呗、信用卡。**不支持货到付款**。 |
| Reply | **目前不支持货到付款**，支持微信、支付宝和银行卡在线支付。 |
| Ground Truth | 正常 |
| 我的判定 | 正常 ✓ |

**为什么容易误报？**
- KB 含否定词"不支持"，reply 也含肯定词"支持"，触发朴素"KB否定+reply肯定"的规则。
- 但 reply 也明确否定了"货到付款"，**KB 和 reply 否定的是同一对象**，reply 中的"支持"指向其他支付方式。

**修复方案**：R_NEG_AFFIRM 仅在 KB 含**强否定**（"暂无"、"当前无"、"无此"、"未标注"、"本品牌为"、"纯线上"）时触发，KB 含"不支持 X"等**普通否定**不触发，避免把"支持 A / B / C"误判为编造。

**仍可能误判的情形**：reply 中"支持 A" 但 A 与 KB 否定对象在字面上看起来不同（如 KB "不支持货到 X 付款" vs reply "支持货到付款"——分词差异）。

### 1.3 `h08` 发货时间 + 快递公司 — "部分正确 + 部分错误"型

| 维度 | 内容 |
|---|---|
| KB | 发货时间：下单后**24 小时**内发货（预售商品除外）。合作快递：**中通/韵达/圆通**。 |
| Reply | 下单后**48 小时**内发货，一般使用**顺丰**快递。 |
| Ground Truth | 政策偏差 |
| 我的判定 | 事实编造（R_PARAM_MISMATCH：KB=24 vs Reply=48） |

**为什么容易漏检/误报？**
- 时效偏差（24h → 48h）容易通过 R_PARAM_MISMATCH 抓到，单位都是"小时"。
- 快递公司（顺丰 vs 中通/韵达/圆通）走 R_FACT_FROM_EMPTY（KB 没"无顺丰"，但 KB 中"快递"配合 _has_specific_entity 不一定能命中"顺丰"）。
- 这次检测恰好通过 R_PARAM_MISMATCH 命中。如果样本中时效数字相同而快递公司不同，可能漏检快递公司部分。

**改进方向**：单独加 R_CARRIER_FAB 规则，匹配"KB 中含"快递"，reply 给出具体快递公司名"。

### 1.4 `h20` 信息遗漏 — "KB 含差异化数据被忽略"型

| 维度 | 内容 |
|---|---|
| KB | 用户评价汇总：约 **30%** 的用户反馈偏大半码，建议脚瘦的用户选小半码。 |
| Reply | 这款鞋尺码**标准**，不偏大也不偏小。 |
| Ground Truth | 信息遗漏 |
| 我的判定 | 关键遗漏（R_OMIT_USER_FEEDBACK，置信度 0.65） |

**为什么这是边界 case？**
- reply 给出的"标准"在严格意义上不是"错"的（鞋码本身可能确实是标准码），只是**遗漏了 KB 中的差异化反馈**。
- 规则依赖 KB 中"用户反馈 / 用户评价 / 注意事项"等关键词，且 reply 给出"标准 / 通用 / 不偏"等"中立"答案。
- 这种 case 即使正确检测，置信度也比较低（0.65），因为本质是"语义对错模糊"。

**改进方向**：
- 用 LLM 做语义级判断（可惜环境无 LLM API）
- 或者构建"评价关键词库"（偏大 / 偏小 / 偏紧 / 偏松）做正反义比对

### 1.5 `h13` 安全误导 — "绝对不能漏"的高危 case

| 维度 | 内容 |
|---|---|
| KB | 含 **视黄醇** 衍生物，**孕妇**及**哺乳期**女性建议咨询**医生**后使用。 |
| Reply | 可以放心使用，孕妇可以放心。 |
| Ground Truth | 安全误导 |
| 我的判定 | 安全误导（R_SAFETY_DISMISS，P0） |

**为什么这条容易漏检？**
- 如果不显式维护 SAFETY_KEYWORDS（孕妇 / 视黄醇 / 医生 等），规则不会触发。
- SAFETY_DISMISSAL_PHRASES（"可以放心使用"等）也容易在 KB 更新时被忽略。

**改进方向**：
- SAFETY_KEYWORDS 应该是**强制维护**的核心词典
- 在生产环境应该配合 NER 模型识别"成分名"、"人群名"

## 二、规则化方法的系统性局限

### 2.1 分类粒度差异

**Ground Truth 8 类**：
- 政策编造 / 参数编造 / 优惠编造 / 信息编造 / 能力越界 / 政策偏差 / 安全误导 / 信息遗漏

**我的体系 5 类**：
- 事实编造（合并上述 4 类）+ 能力越界 + 政策偏差 + 安全误导 + 关键遗漏

**影响**：分类准确率仅 0.35，但二分类准确率 1.0。

**权衡理由**：
- 5 类更聚焦"检测方法"，便于规则化实现
- 4 类（政策编造 / 参数编造 / 优惠编造 / 信息编造）的检测方法高度一致（"KB 无 + reply 有"），合并更工程友好

**如需细分**：可在 R_FACT_FAB 内部加子分类：
```
R_FACT_FAB_TYPE_POLICY    // 含政策术语 → 政策编造
R_FACT_FAB_TYPE_PARAM     // 含具体数字参数 → 参数编造
R_FACT_FAB_TYPE_PROMO     // 含优惠 → 优惠编造
R_FACT_FAB_TYPE_INFO      // 含地址/品牌/其他 → 信息编造
```

### 2.2 不依赖 LLM 的代价

| 能力 | 规则方法 | LLM 方法 |
|---|---|---|
| 复杂语义理解 | 弱 | 强 |
| 维护成本 | 低（白名单 + 正则）| 高（提示工程）|
| 可解释性 | 强（每条规则可追溯）| 弱 |
| 离线运行 | ✓ | ✗ |
| 中文 NER | 弱（需自建词典）| 强 |

### 2.3 潜在风险场景

**容易漏检**：
- KB 中**完全没有否定词**但 reply 错了（如 KB 只说"退货政策是 7 天"，reply 说"30 天"）—— 这条能通过 R_PARAM_MISMATCH 抓 ✓
- KB 中**信息完整但 reply 跳过关键信息**（如 h20 类遗漏）—— 置信度低
- **模糊语义**型（"基本准确" vs "完全准确"）—— 难量化

**容易误报**：
- **列举型** KB（如"支持 A、B、C、D"）+ reply "支持 A、B、C"—— 已通过 _is_semantically_equivalent 缓解
- **修饰性语言**（"我们承诺 24 小时内发货" vs KB "24h 内"）—— 同义改写一般不触发
- **跨句语境**（KB 中"不支持 X" 但 KB 后半句又说"特殊情况下 X 可以"）—— 规则只看整体上下文，难以处理

## 三、如果换到真实生产环境，需要补的工作

1. **NER 接入**：用 HanLP / LAC / 百度 NLP 提取实体（成分、城市、品牌、快递公司）
2. **同义词扩展**：构建业务同义词库（"真皮" = "头层牛皮"，"支持" = "可以" = "能")
3. **LLM-as-judge 兜底**：对规则低置信度（< 0.7）的样本自动转人工 / 调用 LLM 复核
4. **规则版本管理**：每条规则可灰度上线 / 回滚，配合 A/B 测试
5. **规则覆盖率监控**：定期在新数据上跑，统计未触发规则的样本，发现新的幻觉模式

## 四、本数据集上的最终评估

| 指标 | 二分类 | 分类（5 类 vs 8 类）|
|---|---|---|
| Precision | 1.000 | 0.350 |
| Recall | 1.000 | 0.350 |
| F1 | 1.000 | 0.350 |
| Accuracy | 1.000 | 0.350 |

**结论**：
- 二分类层面：完美检测，无漏检无误报
- 分类层面：因为粒度差异（5 类 vs 8 类），分类准确率仅 35%。但所有幻觉都被归入"事实编造"或正确的"能力越界 / 政策偏差 / 安全误导 / 关键遗漏"，且严重程度排序合理
- 对实际生产更有意义的不是"分类完全匹配"，而是"能正确识别幻觉并按严重程度路由人工审核"
